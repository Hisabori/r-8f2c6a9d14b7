# 1.9 통합 거래소 및 Ubuntu 서버

마켓의 **통합 거래소 · 실주문**에서 Binance, BingX, 빗썸, Bitget을 선택합니다. 기존 CSV/실시간 전략은 모의매매만 실행하며 실제 주문과 연결되지 않습니다.

## 서버 준비
서버 파일은 `operator/multiexchange/`에 있습니다. 그 폴더의 README_KO.md에 Ubuntu26.04/Docker/WSL 진단, API키 설정, HTTPS 연결, 시작/중지와 결과 불명 주문 대조 방법이 있습니다. Docker가 없는 현재 환경에서는 먼저 설치 방식부터 확인합니다. Node/nvm 경고는 Python 컨테이너 실행과 별개입니다.

## 앱 사용
1. 사용자가 서버를 구성하고 개인 HTTPS 주소와 서버 접근 토큰을 저장합니다. 거래소 Secret은 앱에 입력하지 않습니다.
2. 서버 상태와 선택 거래소 시세를 조회합니다. 계좌 조회는 서버가 활성화되고 키가 설정되어야 가능합니다. 읽기 토큰은 주문을 제출할 수 없습니다.
3. 거래소/코인/매수·매도/수량/지정가를 입력해 검토합니다. 빗썸은 KRW, 나머지는 USDT입니다.
4. 검토된 주문을 30초 안에 별도 확인해 제출합니다. 입력 변경/화면 이탈 시 다시 검토합니다.
5. 마지막 주문 상태를 확인합니다. 시간초과는 미접수를 뜻하지 않습니다. 서버의 UNKNOWN/PENDING은 신규 주문을 막습니다. 앱 재설치나 서버 원장 삭제로 이 기록을 우회하지 않습니다. 취소 요청은 이미 체결된 거래를 되돌리지 않습니다.

## 검증 기준과 후속 작업
- 이번 범위: 현물 지정가·잔고·상태·취소, 4개 거래소 가짜 전송 계약 테스트, HTTPS 경로/역할/중복 방지·기기 토큰 격리. 실제 계좌 인증·체결·Ubuntu Docker 배포·물리 기기는 별도 검증입니다.
- 사용자 운영 단계: Docker doctor→기본 비활성 서버→개인 HTTPS→시세→API권한 및 계좌 확인→본인이 결정한 한도와 활성화→실제 주문은 사용자가 직접 검토합니다.
- 후속: 거래소별 계좌 유형/지역별 허용 범위, 명시적 주문 동기화, 다중 주문 내역 UI. UNKNOWN을 자동 초기화하거나 자동 재주문하지 않습니다.
- 레거시 CVD/호가 불균형/유동성 증발 연구는 기존 TODO를 따르며 실주문과 연결하지 않습니다.
